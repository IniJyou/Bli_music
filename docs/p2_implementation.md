# P2 本地资料库

2026-11-03 更新。P2 版本 0.2.0 已完成实现和技术验证，用户同意收尾。提交与合并状态见项目计划。

## 使用方式

- 顶部“资料库”提供全部音乐、我喜欢、最近播放和本地歌单。加入队列的曲目自动进入资料库，按 `bvid:cid` 区分同一视频的不同分 P。
- 队列中的“保存歌单”可新建歌单或加入已有歌单；相同分 P 去重。歌单可重命名、调整顺序、移除曲目、删除以及单独导出。
- 曲目支持喜欢、取消喜欢和编辑歌名／歌手。展示名称与原视频、分 P 标题分开保存，歌手与 UP 主也分开。清空手动歌名后恢复默认命名；版本标签继续单独显示。
- 按 `建议/搜索后能直接有添加喜欢.png` 补齐搜索结果行的爱心：关键词、BV／AV 与视频链接均可直接添加或取消喜欢，不必先加入队列。关键词对应 P1，带 `p=` 的链接对应指定分 P；以同一个 `bvid:cid` 与队列、资料库共享喜欢状态，重复操作不会产生重复曲目。已保存的视频信息可直接复用，未保存的结果先读取真实分 P 信息，失败时不显示已喜欢。操作反馈放在搜索标题下方，不遮挡标题。参考截图不作为应用素材。
- 歌单内可搜索歌名、歌手、UP 主、BV 号、原视频和当前分 P 标题。每页 50 首，避免一次创建过多界面节点。搜索期间禁用歌单排序，避免将过滤后的序号误认为原始顺序。
- 单击选择、双击播放，单曲播放加入现有队列；“播放列表”按当前列表顺序替换队列。播放队列上限仍为 500 首，播放更长列表时明确提示，资料库保留全部曲目。
- 真实开始播放时记录最近播放与次数，暂停后继续同一播放过程不重复累计。最近播放可单条移除或清空。

## 保存和恢复

开发期数据默认保存在 `D:\aiworkspace\MyMusic\.data`：

| 位置 | 内容 |
| --- | --- |
| `.data/library.sqlite` | 曲目、歌单、喜欢、播放历史、队列、进度与设置 |
| `.data/library.sqlite-wal`、`-shm` | SQLite 运行中的事务辅助文件 |
| `.data/backups` | 自动及手动生成的 SQLite 备份 |
| `.data/exports` | 原生导出窗口的默认保存目录 |
| `.cache` | 原有开发缓存、临时目录和 Electron 运行资料；与资料库分开 |

`.data` 已加入 Git 忽略。这里只保存歌曲信息和播放状态，音频继续在线流式播放。播放地址不写入资料库或导出文件。

队列变化约 250ms 后保存，播放中每 5 秒保存进度，暂停和跳转也触发保存。正常关闭窗口前，主进程等待界面完成最后一次保存；失败时提供重试、取消退出或保留上次状态退出的明确选择。

重启恢复曲目、顺序、播放模式、当前 CID、进度、场景和最近搜索；默认不解析音源或自动发声，点击播放后重新获取有效音源再跳到保存位置。“备份与设置”可开启启动自动播放。每次启动音量仍为用户已确认的 5%，不保存上次的大音量作为启动值。

P1 仅在内存保存队列，没有可迁移的历史队列文件。从 P2 开始产生持久数据；不会尝试从浏览器或 B站账号恢复个人内容。

## 导入、导出与删除边界

“备份与设置”支持导出整个资料库、导入自己的 Bli Music JSON 文件、手动备份和预览恢复 SQLite 备份。歌单标题右侧另有单独导出入口。网易云与 QQ 音乐的外部歌单匹配仍属于 P4。

- JSON 格式标识 `bli-music-library`，格式版本 1；导入前核对字段、数量、稳定标识与引用关系，文件上限 50MB。界面预览曲目、歌单、喜欢和重复曲目数量，再选择操作。
- 默认“合并”保留现有曲目名称、歌手、队列、进度与设置；喜欢合并保留，已有歌单追加去重，同 ID 歌单保留现有名称。同名但不同 ID 的导入歌单增加导入序号。
- “恢复”替换资料库、队列及设置，暂停当前播放；恢复本身不会立即自动播放。导入文件中的启动自动播放设置在下次启动生效。
- 导出与手动备份前保存最新队列与进度。JSON 文件写入临时文件并刷盘后重命名，取消原生文件选择不改变资料库。
- 删除歌单只删除歌单结构，保留曲目、喜欢、历史和当前队列。从歌单移除也保留资料库曲目。
- 从“我喜欢”或“最近播放”移除只改变相应标记或历史。从“全部音乐”删除则移除所有歌单关系、喜欢、历史与队列中的该曲目，当前曲目被删除时停止播放；确认文案说明实际影响。
- 删除歌单、从资料库删除、清空历史、导入或恢复前自动备份。备份保留在本机，可从设置预览恢复；删除列表项目不代表自动删除旧备份。当前界面展示最近 30 个备份，较早文件仍保留在目录中。

## 存储与隔离

实测现有 Electron 45.1.0 内置 Node.js 24.22.1、SQLite 3.53.4，采用内置 `node:sqlite`；开发用 Node.js 24.16.0 的 SQLite 为 3.53.0。无需下载 better-sqlite3、原生编译工具或新资源。依赖仍为原有 86 个已安装包，当前核对见 `p2_dependency_licenses.json`。

数据库 schema 版本 1，使用 `tracks`、`playlists`、`playlist_tracks` 与 `meta` 表。采用外键、WAL、FULL 同步和事务；导入及多步骤修改整体成功或整体回滚。SQL 参数绑定，所有资料库 IPC 校验输入和主窗口来源，文件路径由原生文件窗口或固定数据目录提供，界面不能传任意路径进行读写。

备份通过 SQLite `VACUUM INTO` 创建完整快照，包含已提交的 WAL 数据；再次只读打开、检查 schema 和导出数据校验通过后，才执行破坏性操作。未知 schema、损坏文件和未来格式明确报错，不创建空库覆盖原有文件。后续 schema 迁移必须先形成同样可验证的备份。

完整恢复或删除曲目会更新播放状态代次；旧的进度请求和延迟播放记录不能把删除或恢复前的队列重新写回。界面只派生展示名称，元信息保留原始字段；保存时过滤临时音源与未知凭据字段。

恢复过程中处理了两项事件边界：旧音频清空产生的时间事件不再覆盖刚恢复的进度；程序关闭旧对话框的延迟事件不再误关快速重开的备份窗口。

实现依据：[Node.js 24 SQLite 文档](https://nodejs.org/download/release/latest-v24.x/docs/api/sqlite.html)、[SQLite VACUUM INTO](https://sqlite.org/lang_vacuum.html#vacuum_with_an_into_clause)。本项目实际运行环境另经离线功能探测和真实文件检查。

## 备份与故障恢复

日常优先使用应用内的备份或导出功能；运行时不要只复制 `library.sqlite` 而遗漏事务辅助文件。完整目录复制请先退出应用。

若资料库损坏到无法打开，应用保留原文件并报错。先退出应用并完整保留原 `.data` 目录及辅助文件；在另一个目录保存副本后，可用 `.data/backups` 中已验证的独立 SQLite 备份重建新的 `.data/library.sqlite`。恢复前保留原目录，不覆盖仅存的一份损坏数据。此类人工文件恢复需要核对实际路径；应用内恢复入口适用于当前资料库可以正常打开的情况。

当前版本未实现安装包的数据目录迁移、跨设备同步或加密备份；打包和升级路径在 P5 验证。默认无遥测、个人账号与额外网络服务。
